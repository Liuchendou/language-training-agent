## 1. 目标与验收标准

**目标一句话：** 把现在只在本机 `127.0.0.1:8000` 上跑的后端搬到一个**公网可达、带 HTTPS** 的地址，让手机浏览器直接打开就能用，不必在手机上装任何东西。

**验收标准（逐条可测）：**

| # | 验收项 | 判定方式 |
|---|---|---|
| 1 | 手机浏览器打开 `https://<部署地址>/` 能看到首页 | 目视 |
| 2 | `https://<部署地址>/api/health` 返回 `{"status":"ok"}` | 浏览器直接访问 |
| 3 | `https://<部署地址>/api/materials/import-capabilities` 返回 `ready: true` | 同上 |
| 4 | 素材音频能在手机上播放 | 播放 `/api/materials/<id>/audio` |
| 5 | **能用手机麦克风录音并拿到朗读评分** | 训练页录音后出现三维结果 |
| 6 | 从本机之外（如 4G 网络）访问同样成立 | 关闭 WiFi 用流量重测 |

第 5 条是关键——它区分了「能打开页面」和「功能真的可用」，也是第 3 节要解决的卡点。

## 2. 现状事实（可在仓库内核实）

| 事实 | 出处 |
|---|---|
| 服务默认绑回环地址：`--host 127.0.0.1 --port 8000` | `start-local.bat` |
| 前端与后端**同源**托管：后端启动时把 `frontend/dist` 挂到 `/` | `backend/app/main.py`（`app.mount("/", StaticFiles(...))`） |
| 所有 API 路由前缀为 `/api` | `backend/app/api/routes.py:45` |
| 前端**没有任何硬编码后端地址**——全部走相对路径 | 全量扫描 `frontend/src`，唯一的 `https://` 出现在 `ImportFromUrlPanel.jsx:109` 的输入框 placeholder 文本里 |
| 音频播放用相对路径 | `Views/TrainingView.jsx`、`DictationPanel.jsx:190`、`ReadingPanel.jsx:103`、`WeeklyPanel.jsx:63` 均为 `/api/materials/${id}/audio` |
| 录音依赖浏览器的 `getUserMedia` | `frontend/src/wavRecorder.js:42`（`navigator.mediaDevices.getUserMedia({audio:true})`） |
| **后端没有配置任何 CORS 中间件** | 在 `backend/app` 全量搜索 `CORS` / `add_middleware` / `allow_origins`，无匹配（只有一个 `no_cache_html` 中间件） |
| 数据是本地 SQLite 单文件 | `backend/app/config.py:15`，路径 `data/language_training.sqlite3` |
| 项目根目录可重定位，且多个路径可由环境变量覆盖 | `backend/app/config.py:7`（`Path(__file__).resolve().parents[2]`）与 `config.py:58-65`（`LTA_PROJECT_ROOT` / `LTA_DATABASE_PATH` 等） |
| 外部依赖体积：`tools/` 444 MB（ffmpeg 303 MB + 模型 142 MB）；`.venv/` 411 MB；`node_modules/` 114 MB | 2026-10-06 实测 |
| 无认证：任何能访问到地址的人都能读写这套数据 | 搜索结果中无 auth 相关中间件/依赖 |

**两个有利结论**（都是上表的直接推论）：

- 因为前端全走相对路径、且后端本来就把前端挂在同一进程上，**同源部署不需要改任何前端代码**，也不需要 CORS。
- 项目根目录是推导出来的，不是写死的，所以换机器、换路径不用改代码。

## 3. 真正的卡点（按严重度排序）

### 3.1 录音在非安全上下文下会被浏览器拒绝

`wavRecorder.js` 用的是 `getUserMedia`。【基于模式观察】浏览器只在「安全上下文」下授予麦克风权限：`https://` 或 `http://localhost` 算，`http://<公网IP>:端口` 不算。

**这条决定了方案必须带 HTTPS，不能只是「端口打开」。** 这是第 1 节验收标准第 5 条的成败点。

### 3.2 监听地址写死在启动脚本里

`start-local.bat` 硬编码 `127.0.0.1`。要对外提供服务，必须改成绑 `0.0.0.0` 或具体网卡地址。当前没有对应的 `LTA_HOST` / `LTA_PORT` 环境变量（`config.py` 的 28 个配置项里没有这两项）。

### 3.3 无认证

一旦有公网地址，任何知道地址的人都能看到素材库、训练记录，并能写入。**这不只是隐私问题，也意味着任何人都能触发 ASR 这类 CPU 密集操作。**

### 3.4 没有 CORS 中间件（仅在前后端拆分部署时才会暴露）

如果选择「把前端放 CDN、后端单独部署」这种拆分方案，浏览器会因跨源而拦掉所有 `/api` 请求，届时必须加 CORS。**同源部署则完全不需要。**

### 3.5 素材与模型是本地文件，不是无状态服务

- ffmpeg 与语音模型合计 444 MB，必须随部署环境一起准备。
- ASR 是**本地推理**（faster-whisper + ctranslate2，CPU `int8`），云主机规格直接决定导入一篇素材要等多久。

## 4. 两条可选路线

### 路线 A：隧道（把本机服务映射到公网）

用 cloudflared / Tailscale Funnel 一类工具，给本机的 `127.0.0.1:8000` 分配一个带 HTTPS 的公网地址。

- 优点：不用买服务器、不用备案、不用改代码里的路径；隧道服务自带 HTTPS，直接绕过 3.1。
- 限制：**本机必须常开**，手机才有得连——本质仍是「本机是服务器」，只是把入口挪到了公网。
- 前置：需要一个隧道服务账号。【无法验证】各家免费额度与域名策略会变，需在执行时现场确认。

### 路线 B：云服务器（真正「云端后端」）

把项目部署到一台有公网 IP 的云主机，配 HTTPS（证书或云厂商的负载均衡），手机直接访问。

- 优点：不依赖本机开机。
- 代价：需要域名；若用中国大陆的服务器对外提供 Web 服务，【基于模式观察】通常涉及 ICP 备案。
- 需要额外处理：3.2 的监听地址、3.3 的认证、3.5 的模型与算力。

**选择建议：** 如果目的是「摆脱本机常开」，只有路线 B 成立；如果只是「偶尔在外面用一下」，路线 A 成本低得多。**请在开工前明确选哪条**，两条路的工作量差一个数量级。

## 6. 需要你在新任务开工前确认的事项

1. **走路线 A 还是 B？**（决定全部工作量）
2. 有没有可用的**域名**？能否接受备案？
3. 是否接受把**训练数据放到公网环境**？（现在数据是本地 SQLite，含你的学习记录）
4. 需要**认证**吗？共享口令够了，还是要多用户？
5. 云主机预算与**算力规格**？ASR 在 CPU 上跑，规格越低导入越慢。
6. 部署目标是 **Windows 还是 Linux**？现在 `tools/ffmpeg/bin/*.exe` 是 Windows 专用，Linux 上要换成系统 ffmpeg（后端会命中 PATH 分支，代码无需改）。

## 7. 已知风险

| 风险 | 依据 | 应对 |
|---|---|---|
| 大文件下载在受限链路下会断流 | 2026-10-06 实测：gyan.dev 的 ffmpeg 包下载至数 MB 后停滞 | `prepare_assets.py` 已实现断点续传 + 自动重试 + 零进展熔断 |
| ASR 首次加载模型有延迟与内存占用 | 模型 `model.bin` 实测 145,217,532 字节 | 部署后在自检接口确认 `whisper_model_local: true`，避免首次识别时联网下载 |
| 云主机若为 ARM 或无 AVX 指令集，`ctranslate2` 行为未知 | 本机实测为 Windows x86_64 | 【无法验证】需在目标主机上实跑一次转写确认 |
| SQLite 在多设备并发写入下的表现 | 本机实测只有单机使用 | 【无法验证】需在目标环境压测；必要时改为串行化写入 |
| 【基于模式观察】手机浏览器对 `getUserMedia` 的策略差异 | 各浏览器实现可能不同 | 验收时至少覆盖一种主流移动浏览器，并实测第 1 节第 5 条 |
